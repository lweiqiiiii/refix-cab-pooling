01

Discovery

Core rules confirmed; Discovery-to-Design transition approved

The problem

Staff need journeys from home to the event venue or back home. REFIX collects names and locations/postal codes and groups nearby staff. Full-time staff manually compare postal codes; staff counts vary. Planning effort, costs, and errors have not been measured.

What success looks like

Fewer cabs is the first priority, shorter passenger journeys second. Only staff locations should affect grouping; the venue must not. Pasted names and postal codes are sufficient; the prototype otherwise meets the user’s intent. A measurable baseline remains open.

Scope and commitments

Included

The existing paste/group/copy app supports four seats, three postal-code stops, and 12-minute two-stop / 18-minute three-stop total budgets. The refined interface uses full-width cab groups, clear headings and numbered stops, with compact unassigned-entry details for laptops and phones.

Excluded or deferred

Booking, payment, dispatch, new accounts, persistent staff history, and deployment remain outside this refinement.

Questions and dependencies

The user specifies four passengers, at most 12 minutes total for two stops, and at most 18 minutes total for three stops. Same-house passengers share one location and must stay in the same cab unless choosing different drop-off locations. At most three home locations are allowed. Three-stop drive times are added across both consecutive drives. A 13-minute drive plus a 5-minute drive is valid for three stops; a standalone 13-minute two-stop route is not valid. The 12-person sample includes three area-only entries, which current parsing skips. Missing postal codes must be flagged in the app. Matching postal codes define one shared pickup/drop-off party. Parties above four must be flagged for manual arrangement without splitting. API health, costs, data access, and ownership remain unverified.

Developer guide

System context, implementation, and operation

The existing app has been refined in place. Eleven mocked automated tests, production compilation, and desktop/mobile browser checks pass. A bounded 100-location synthetic check preserved every assignment invariant; live Google validation has not occurred.

Requirements and system context

Workflow and business rules

Four passengers and three postal-code stops remain the maximum. Two stops allow at most 12 minutes total; three stops allow at most 18 minutes total. Matching-code parties stay together. Above four passengers requires manual arrangement. Venue is excluded; selection prioritizes cab count before total inter-stop driving time.

Systems and dependencies

The user reports Google APIs for locations and drive times. Source shows a Next.js/React page submitting postal-code counts to /api/group. Integration health and production status remain unverified.

Requirements and unresolved constraints

lib/group.mjs enforces four seats and inclusive route budgets: 720 seconds for two stops, 1080 seconds total for three stops. Nearby route candidates and a 10,000-node search bound prevent a global-optimum claim. Real-event acceptance and live provider/quota behavior remain unverified.

Reference: Requirements and acceptance criteria · Open questions and constraints

Architecture and interfaces

Implemented refinement in existing app paths. Provider behavior was verified with mocks; Google account configuration remains unverified.

Data path: pasted list → postal-code parties → missing/manual flags → trusted directed route data → feasible three-stop candidates → cab-count-first selection → names and ordered assignments in the browser. Venue data is excluded.

The user-directed A2 build uses bounded nearby candidates and up to 10,000 search nodes, returning a valid best-found partition. The interface states that the fewest possible cabs are not guaranteed.

Design evidence: Synthetic checks and limits · Selection options

Components and interfaces

Keep the browser page for names and display, POST /api/group for input validation and Google requests, and lib/group.mjs for pure route/group selection. Return ordered stops and per-leg times plus explicit unresolved/manual categories. Update all callers and output formats together.

Data and security

Names stay in the browser; the server receives postal-code counts. The Google key stays server-side. Trusted server caching replaces unsigned client durations as route evidence. No persistent staff history or new database is proposed. Access and operational ownership remain unverified.

Deployment and design decisions

Keep the current deployment path; no deployment is authorized. Provider errors must not become no-route results. Unresolved people remain visible. The existing 100-code guard, 15-km nearby filter, and eight-destination bound remain. At most 800 directed route elements are considered at that cap; smaller runs may use more than old one-direction checks. External Google quotas were not inspected or changed; these app guards do not guarantee free use.

Local setup and prototype

Prerequisites and configuration

Existing Next.js/React dependencies are unchanged. GOOGLE_MAPS_API_KEY stays in ignored server-side environment configuration. API access and actual account quotas require owner verification before real grouping.

Run the application

From the repository root, use npm run dev and open its printed URL. Browser verification used npm run dev -- --hostname 127.0.0.1 --port 3011. Run npm test for mocked checks and npm run build for compilation.

Behavior and limitations

Prototype A2 is implemented locally. All automated/browser verification uses synthetic provider data. Server memory caches expire after 24 hours for geocodes and five minutes for drives. Cold starts may repeat lookups. Live credentials, quotas, and provider retention terms remain unverified.
